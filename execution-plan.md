# Engineering Execution Plan: AI SMS Wrapper

Based on the original `design-sms-wrapper.md` and our engineering review, here is the finalized execution plan for building the Micro-Finance SMS wrapper.

## Architecture
- **Stack:** Next.js (Frontend) + NestJS (Backend) + Redis (BullMQ).
- **Monorepo:** Utilizing the existing `officialsaptacode/pn3` monorepo structure to share types between frontend and backend.
- **Authentication:** Hosted Auth (e.g., Clerk or Supabase) with JWTs. The Next.js frontend will pass the JWT to the NestJS backend to ensure only authorized managers can schedule campaigns.
- **CSV Uploads:** Large CSV files will be uploaded directly to Cloud Storage (S3/R2) using Presigned URLs generated by the backend. This bypasses Vercel/Next.js payload limits and prevents memory crashes.

## Core Flow
1. **Template Drafting:** Manager uses Next.js UI to draft an SMS template. System 2 (LLM) assists in generating a polite, 160-character template.
2. **Compliance Check:** System 1 (`convaiinnovations/laya`) evaluates the template for spam/compliance.
3. **Execution Setup:** Manager uploads the CSV via Presigned URL. NestJS reads the file from storage.
4. **Queueing (BullMQ):** 
   - **Job Granularity:** We will use chunked jobs (e.g., 100 SMS per job) or 1 job per SMS to guarantee exactly-once delivery and prevent duplicate sends in case of partial API failures.
   - **Rate Limiting:** BullMQ will be configured with a strict concurrency cap / rate limiter to respect AkashSMS's API limits, preventing 429 Too Many Requests errors.

## Testing Strategy
- **SMS API Mocking:** We will use MSW (Mock Service Worker) and a dedicated "Dry Run" flag in the environment. This ensures automated tests verify the HTTP request logic perfectly without hitting the real AkashSMS API and draining real funds.
